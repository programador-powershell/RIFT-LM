1. Research question

What is the smallest executable representation that preserves every unit of a frozen capability contract under the target VLB runtime?

Efficiency is optimized only after retention. Aggregate perplexity, cosine or average accuracy may hide local regressions, so VLB separates conversion fidelity, native execution correctness and behavioral certification.

The high-precision source may be Safetensors or a high-precision GGUF container, but the final inference path is VLB-owned. GGUF/GGML, llama.cpp, PyTorch, Transformers, vLLM and ONNX Runtime are not accepted as hidden fallback engines in a native VLB certification.

3. RAM-aware precision

VLB does not assume that every x86 machine has the same RAM budget. A deployment profile may keep bulk matrices at Q4, sensitive matrices at Q5/Q8 and small state/norm tensors in source precision, then spend available RAM headroom on precision promotion. Lower precision is never accepted merely to make a model fit; the behavioral contract decides whether a profile survives.

4. VLB container and native kernels

The VLB container stores tensor layout, codec, dimensions, hashes, provenance and model metadata required by the native executor. Low-bit matrix kernels are implemented and tested independently against scalar reference paths on real tensors from the converted artifact. Kernel equivalence is necessary but is not full-model retention.

5. Model execution

VLB is a technology/runtime rather than a requirement that imported weights be rewritten into a single neural topology. The runtime keeps the imported execution graph semantics—such as Qwen3.5 hybrid attention/DeltaNet, MoE routing, or Muse/Glimmer topology—while container, tensor codecs, x86 kernels, memory management, certification and AMT are VLB-owned.

6. KR100

KR100 ⇔ every frozen proof unit passes

no global average may hide a failed unit
no later gain may compensate for a regression
no deployment profile is verified before native replay

For public reference models, the retention contract may include their published benchmark harnesses. For project-owned models, a frozen reference ledger is used. Numerical conversion metrics remain diagnostics, not substitutes for behavioral evaluation.

7. Real benchmark publication

The VLB desktop pipeline publishes executed measurement records through the repository's authenticated ingest API. The server commits those records to the measurement ledger on main; Vercel then serves the updated paper. Records are marked simulated: false, and a run cannot become primary/verified unless native runtime and proof gates actually pass.

8. AMT

AMT is teacher-free. There are no teacher logits, KL targets or teacher hidden states. Learning modifies model-owned canonical trainable state. Deployment bytes are derived from that canonical state and must be re-certified after learning. Minimum sufficient exposure, fresh validation, rollback and KR100 govern promotion.

10. Current targets

Current experimental imports include BitGlimmer, Ornith/Qwen3.5-class models, Air-1 and larger Qwen3.8-class candidates. Each model may use a different execution adapter, but all adapters terminate in the same VLB container/runtime/proof contract. Unsupported architecture operations must fail explicitly; the test application does not simulate a successful inference path.

11. Falsification

A VLB profile is rejected if it cannot reproduce the frozen behavioral contract, if a native executor needs an undeclared fallback runtime, if compression gains disappear once retention is restored, or if benchmark settings differ materially from the source/reference run.
